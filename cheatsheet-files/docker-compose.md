# docker-compose

Docker Compose defines a multi-container application in a YAML file and drives its whole lifecycle with one command. On an on-premise server it is the usual way to run a stack of services with their networks, volumes, and startup ordering without pulling in an orchestrator.

## docker-compose - Check the Version and the v1 Versus v2 Split

Compose v2 is a Go plugin for the Docker CLI and is invoked as a subcommand, with a space.

```
docker compose version
```

Compose v1 was a separate Python program installed as its own binary, invoked with a hyphen. Older on-prem boxes often still have it on PATH, and it can be a completely different build from the plugin, so check both before trusting a command you copied from a runbook.

```
docker-compose --version
```

Print just the number, which is what a provisioning script should test:

```
docker compose version --short
```

The differences that bite in practice: v2 requires project names to be lowercase and rejects anything else instead of silently normalising it, v2 names containers `<project>-<service>-<n>` with hyphens where v1 used underscores, `--no-ansi` is deprecated in favour of `--ansi never`, and on `logs` the short flag `-t` now means `--timestamps` while `--tail` takes `-n`. Everything below is written for v2.

## docker-compose - Validate and Render the Effective Configuration

Parse, interpolate, merge, and print the file Compose will actually act on. This is the single most useful debugging command, because it resolves variables, applies overrides, and normalises shorthand without starting anything.

```
docker compose config
```

Validate only, printing nothing and exiting non-zero on error. Use this as a CI gate and in a pre-deploy check:

```
docker compose config -q
```

Render as JSON so a script can query it:

```
docker compose config --format json
```

Write the fully resolved file to disk, which is how to ship one flattened artifact to a server instead of a directory of overrides:

```
docker compose config -o rendered-compose.yaml
```

Print a content hash per service, useful for deciding whether a redeploy is actually needed:

```
docker compose config --hash '*'
```

## docker-compose - List Services, Volumes and Networks From the Config

Print the service names one per line, which is the reliable way to loop over a stack in a shell script.

```
docker compose config --services
```

Print the named volumes the project declares. These are the volumes `down --volumes` would destroy, so read this before running it:

```
docker compose config --volumes
```

List the declared networks, the profile names, and the images the stack resolves to:

```
docker compose config --networks
docker compose config --profiles
docker compose config --images
```

Note that `--services` omits services that are gated behind a profile until that profile is enabled.

## docker-compose - Choose the Compose Files

Point at a file explicitly instead of relying on discovery of `compose.yaml` or `docker-compose.yml` in the working directory.

```
docker compose -f /srv/app/compose.yaml ps
```

Stack multiple files to layer environment-specific overrides. Later files win, and the merge is per-key: scalars are replaced, most lists are appended.

```
docker compose -f compose.yaml -f compose.prod.yaml up -d
```

Because lists append by default, a base `ports:` entry survives into the override. Tag the key with `!override` in the later file to replace the list outright instead:

```
services:
  api:
    ports: !override
      - "127.0.0.1:8080:8080"
```

Set the same stack in the environment so every later command picks it up, using `:` as the separator on Linux:

```
export COMPOSE_FILE=compose.yaml:compose.prod.yaml
```

Read the file from standard input, which is handy when it is generated by a template:

```
render-config | docker compose -f - config
```

## docker-compose - Set the Project Name

The project name prefixes container, network, and volume names, and it defaults to the directory basename. On a host running several stacks that default collides the moment two checkouts share a directory name, so set it explicitly.

```
docker compose -p acme-prod up -d
```

Or pin it in the environment or the `.env` file:

```
export COMPOSE_PROJECT_NAME=acme-prod
```

With `-p acme-prod`, a volume declared as `pgdata` becomes `acme-prod_pgdata` and the default network becomes `acme-prod_default`. v2 rejects uppercase or otherwise invalid names rather than rewriting them.

Run from elsewhere while keeping relative paths and the `.env` file resolving against the stack directory:

```
docker compose -f /srv/app/compose.yaml --project-directory /srv/app config
```

## docker-compose - Bring a Stack Up

Create and start everything in the background. This is idempotent: containers whose configuration and image are unchanged are left alone.

```
docker compose up -d
```

Rebuild images from their build context first, so a code change is actually picked up:

```
docker compose up -d --build
```

Recreate containers even when nothing changed, which is how to force a clean restart after fixing something outside the compose file:

```
docker compose up -d --force-recreate
```

Start one service without pulling its dependencies up with it. Useful when the database is already running and you only want to cycle the app:

```
docker compose up -d --no-deps api
```

Delete containers left behind by services that no longer exist in the file:

```
docker compose up -d --remove-orphans
```

Always check the registry for a newer image instead of using whatever is cached locally:

```
docker compose up -d --pull always
```

Create the containers without starting them, when you want to inspect or `cp` into them first:

```
docker compose create
```

## docker-compose - Wait for a Stack to Become Healthy

Block until every service is running or healthy, then exit. Without this, `up -d` returns as soon as the containers are created, which makes deploy scripts race against startup.

```
docker compose up -d --wait
```

Bound the wait so a broken deploy fails the pipeline instead of hanging:

```
docker compose up -d --wait --wait-timeout 120
```

## docker-compose - Gate Startup on Health Checks

`--wait` and dependency ordering only mean something if services declare a health check. Compose then knows when a container is genuinely ready rather than merely started.

```
services:
  db:
    image: postgres:16-alpine
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s
```

Make a dependent service wait for that health check to pass instead of merely for the container to exist. `service_started` is the default and only guarantees the process was launched, which is why applications otherwise crash-loop against a database that is still initialising.

```
services:
  api:
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_started
```

## docker-compose - Scale a Service

Override the replica count at start time. Only works for services that do not publish a fixed host port, since two replicas cannot bind the same port.

```
docker compose up -d --scale worker=4
```

Change the count of an already running stack without touching the rest:

```
docker compose scale worker=6
```

Scale several services in one call, and leave dependencies alone:

```
docker compose scale worker=6 api=2 --no-deps
```

## docker-compose - Tear a Stack Down

Stop and remove the containers and the default network. Named volumes and images are kept, so data survives.

```
docker compose down
```

Also delete the named volumes declared in the file plus anonymous volumes. This destroys database contents and is not recoverable — read `config --volumes` first and be certain the project name is the one you think it is.

```
docker compose down --volumes
```

Remove the images too. `local` drops only images built by this project without a custom tag, `all` drops every image any service used, including ones pulled from a registry and possibly shared with other stacks:

```
docker compose down --rmi local
```

Clean up containers for services that were deleted from the file, and give slow services longer than the default to shut down:

```
docker compose down --remove-orphans -t 60
```

## docker-compose - List Containers and Projects

Show the containers of the current project with their state, health, and port mappings.

```
docker compose ps
```

Include stopped and exited containers, which is the only way to see a service that died on startup:

```
docker compose ps -a
```

Filter by state, and print machine-readable output:

```
docker compose ps --status exited
docker compose ps --format json
```

Print only IDs, for piping into other tooling:

```
docker compose ps -q
```

List every Compose project the daemon knows about, not just the current one. On a shared on-prem host this is how to find out what is already running before you deploy over it:

```
docker compose ls -a
```

## docker-compose - Read Logs

Print the combined logs of every service in the project, prefixed with the service name.

```
docker compose logs
```

Follow the stream, starting from the last few hundred lines rather than the whole history. Note that `--tail` is `-n` in v2; `-t` now means timestamps.

```
docker compose logs -f -n 200
```

Restrict to one service and add timestamps:

```
docker compose logs -f -t api
```

Bound the window by time, which is how to pull just the logs around an incident:

```
docker compose logs --since 30m --until 10m api
```

Select one replica of a scaled service:

```
docker compose logs --index 2 worker
```

Drop the service-name prefix and colours so the output can be fed to a parser:

```
docker compose logs --no-log-prefix --no-color api > api.log
```

## docker-compose - Execute a Command in a Running Container

Run a command inside a container that is already up. This is the counterpart to `run`: it attaches to the live service instead of creating a new container.

```
docker compose exec api env
```

Open a shell for interactive debugging:

```
docker compose exec api /bin/sh
```

Disable TTY allocation. Required whenever the command runs from a script, a cron job, or CI, where no terminal is attached:

```
docker compose exec -T db psql -U postgres -c '\l'
```

Run as another user, from another directory, with extra environment:

```
docker compose exec -u root -w /var/log -e LOG_LEVEL=debug api ls
```

Target one replica of a scaled service:

```
docker compose exec --index 2 worker hostname
```

## docker-compose - Run a One-Off Container

Start a new container from a service definition, run a command, and exit. Use this for migrations, backups, and admin tasks; unlike `exec` it does not need the service to be running, and it does not join the service's port mappings by default.

```
docker compose run --rm api python manage.py migrate
```

`--rm` is what stops these throwaway containers accumulating. Without it they persist in `ps -a` forever.

Skip starting the declared dependencies, when you only want the image and not the rest of the stack:

```
docker compose run --rm --no-deps api sh
```

Replace the entrypoint, which is how to get a shell in an image whose entrypoint is the application itself:

```
docker compose run --rm --entrypoint sh api
```

Pass environment and publish the service's declared ports for this run:

```
docker compose run --rm -e DRY_RUN=1 --service-ports api ./import.sh
```

Disable TTY allocation for non-interactive use:

```
docker compose run --rm -T api ./report.sh > report.txt
```

## docker-compose - Build Images

Build every service that declares a build context.

```
docker compose build
```

Build from scratch, ignoring the layer cache. Reach for this when a `RUN apt-get` layer is serving stale package metadata:

```
docker compose build --no-cache
```

Refresh the base image before building, so `FROM debian:12` picks up the current tag rather than the copy pulled months ago:

```
docker compose build --pull
```

Pass build arguments, and build only named services:

```
docker compose build --build-arg APP_VERSION=1.4.2 api worker
```

Build and push in one step, and also build transitive dependencies:

```
docker compose build --push --with-dependencies api
```

Check the build configuration without producing an image:

```
docker compose build --check
```

## docker-compose - Pull and Push Images

Download the images every service needs, ahead of a deploy window so the actual restart is fast.

```
docker compose pull
```

Skip services that would be built locally, and keep going when one registry is unreachable:

```
docker compose pull --ignore-buildable --ignore-pull-failures
```

Force a re-check of every tag instead of skipping images already present:

```
docker compose pull --policy always
```

Push the built images to their registries:

```
docker compose push
```

Push only what succeeds, and include images of declared dependencies:

```
docker compose push --ignore-push-failures --include-deps
```

## docker-compose - Start, Stop, Restart and Pause Services

Stop containers without removing them, keeping their filesystems and configuration for a later `start`.

```
docker compose stop
```

Start previously created containers again. This does not re-read the compose file, so configuration changes need `up`, not `start`:

```
docker compose start
```

Restart one service, leaving anything that depends on it alone:

```
docker compose restart --no-deps api
```

Give a service longer than the default ten seconds to shut down cleanly, which matters for databases and queue workers:

```
docker compose stop -t 60 db
```

Freeze the processes in a container without stopping it, then resume. Useful for taking a consistent snapshot of a volume:

```
docker compose pause db
docker compose unpause db
```

## docker-compose - Kill and Remove Containers

Send a signal straight to the container's main process, bypassing the graceful shutdown that `stop` performs.

```
docker compose kill api
```

Send a specific signal, for example to make a process reload its configuration or dump state:

```
docker compose kill -s SIGHUP nginx
```

Remove stopped containers without touching volumes, networks, or images:

```
docker compose rm -f
```

Stop the containers first if they are still running, and drop their anonymous volumes. Named volumes are untouched, but any data written outside a volume is lost:

```
docker compose rm -s -f -v worker
```

## docker-compose - Use Environment Files and Interpolation

Compose interpolates `${VAR}` in the compose file from the shell environment and from a `.env` file sitting next to it. The shell wins over `.env`.

```
services:
  api:
    image: registry.example.com/app/api:${APP_VERSION:-dev}
    environment:
      LOG_LEVEL: ${LOG_LEVEL:-info}
      DB_PASSWORD: ${DB_PASSWORD:?DB_PASSWORD must be set}
```

`${VAR:-default}` substitutes the default when the variable is unset *or empty*; `${VAR-default}` substitutes only when it is unset, so an explicitly empty value stays empty. `${VAR:?message}` makes the variable mandatory and fails the command with that message. A literal dollar sign is written `$$`.

Point at a different environment file. A single `--env-file` replaces `.env` entirely rather than adding to it, so anything only defined in `.env` reverts to its default:

```
docker compose --env-file prod.env up -d
```

Stack several files when you want a shared base plus per-host secrets; later files win:

```
docker compose --env-file common.env --env-file host.env config
```

Show every variable the file references, with its default. Run this before handing a stack to someone else:

```
docker compose config --variables
```

Dump the environment Compose is interpolating from, and render the file with the substitutions left in place so you can see the raw template:

```
docker compose config --environment
docker compose config --no-interpolate
```

## docker-compose - Enable Optional Services With Profiles

Attach a profile to services that should not start by default, such as backup jobs, seeders, or a debug proxy.

```
services:
  backup:
    image: postgres:16-alpine
    profiles: ["ops"]
    command: ["pg_dump", "-h", "db", "-U", "postgres", "-f", "/dumps/app.sql"]
```

Without the profile the service is invisible to every command, so the default `up` stays lean. Enable it explicitly:

```
docker compose --profile ops up -d
```

Enable several, or set them for the session:

```
docker compose --profile ops --profile debug config --services
export COMPOSE_PROFILES=ops,debug
```

Confirm which profiles a file declares:

```
docker compose config --profiles
```

## docker-compose - Inspect Processes and Resource Usage

Show the processes running inside each container of the project, without needing a shell in the image.

```
docker compose top
```

Restrict it to one service:

```
docker compose top db
```

Stream live CPU, memory, network, and block I/O per container:

```
docker compose stats
```

Take a single snapshot instead of a live stream, which is what a monitoring script wants:

```
docker compose stats --no-stream --format json
```

## docker-compose - Inspect Images and Published Ports

List the images backing the project's containers with their tags and sizes.

```
docker compose images
```

Look up which host address and port a container port was actually published on. Essential when the host port was left to Docker to assign, or when replicas each got an ephemeral port:

```
docker compose port api 8080
```

Query a UDP binding or a specific replica:

```
docker compose port --protocol udp --index 2 collector 514
```

List the volumes the project's services are using:

```
docker compose volumes
```

## docker-compose - Copy Files To and From a Service

Copy a file from the host into a running container, for example to drop in a corrected configuration without rebuilding.

```
docker compose cp ./nginx.conf nginx:/etc/nginx/nginx.conf
```

Copy something out, such as a crash dump or a generated report:

```
docker compose cp db:/tmp/dump.sql ./dump.sql
```

Preserve ownership, follow symlinks, and target one replica:

```
docker compose cp -a -L --index 2 worker:/var/log/app.log ./worker2.log
```

## docker-compose - Stream Events and Block Until Exit

Watch container lifecycle events for the project as they happen. This is how to catch a container that is restarting in a loop too quickly to see in `ps`.

```
docker compose events
```

Emit JSON for a log shipper, and replay a past window:

```
docker compose events --json --since 1h --until 30m
```

Block until the named services' containers stop, returning the exit code. Use it to make a batch job's compose stack behave like a foreground command in a script:

```
docker compose wait migrate
```

Tear the whole project down as soon as the first container exits:

```
docker compose wait migrate --down-project
```

## docker-compose - Sync Source Into Running Containers

`watch` monitors the build context and applies changes to running containers, either by syncing files or by rebuilding. It needs a `develop.watch` block in the service definition.

```
services:
  api:
    build: ./api
    develop:
      watch:
        - action: sync
          path: ./api/src
          target: /app/src
        - action: rebuild
          path: ./api/requirements.txt
```

Start the stack and begin watching:

```
docker compose watch
```

Watch without starting anything first, when the stack is already up:

```
docker compose watch --no-up api
```

Equivalently, start and watch in one command:

```
docker compose up -w
```

## docker-compose - Preview a Command Without Executing It

Every mutating subcommand accepts a global `--dry-run` that prints the actions Compose would take against the daemon and changes nothing. Use it before a destructive operation on a production host.

```
docker compose --dry-run up -d
```

Check exactly what a teardown would remove before committing to it:

```
docker compose --dry-run down --volumes --rmi local
```
